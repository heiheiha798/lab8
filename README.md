SRAM模型本身是“读地址后，下一个周期数据有效”的同步SRAM。这通常意味着读取一个数据需要 1个周期的延迟。
Testbench代码 tb_sram_c_raddr_B = ...; @(posedge clk); @(posedge clk); 在设置地址后，第一个 @(posedge clk) 是地址设置并等待SRAM内部处理的周期，第二个 @(posedge clk) 是数据有效后TB进行采样的周期。
所以，Testbench的这种写法是正确地为这种1周期延迟的同步SRAM模型设计的。从TB发出一个读请求（设置地址）到TB得到数据，总共消耗了 2个TB时钟周期 的时间流逝。
周期T0: TB设置地址。
周期T1: SRAM内部处理，数据在T1结束时输出到 rdata_B。TB等待。
周期T2: TB采样 rdata_B。
所以，这不是Testbench设置的问题，而是正确地匹配了SRAM模型的行为。 如果SRAM是组合逻辑读（地址变化，数据立刻变化，不常见于真实SRAM），或者有不同的流水线级，TB的读方式才需要改变

好的，我们来整合数据加载（Loader）、数据格式化（Data Formatter）和脉动阵列计算（Systolic Array）的完整流程，并基于您的代码和日志，梳理出一个精确到周期的时序关系。

整个加速器的工作流程可以划分为几个连续或重叠的宏观阶段：

1.  **数据加载 (Data Loading)**: `loader` 模块从主存读取A和B的tile数据，写入片上SRAM。
2.  **流水线同步 (Pipeline Synchronization)**: 在加载和计算之间的一个短暂的准备阶段。
3.  **数据格式化与馈送 (Data Formatting & Feeding)**: `data_formatter` 模块从片上SRAM读取数据，生成倾斜的波前，并送入脉动阵列。此阶段与PE计算高度重叠。
4.  **PE计算 (PE Calculation)**: `sa_enhanced` 模块中的PE阵列执行矩阵乘法。
5.  **结果锁存 (Result Latching)**: `sa_enhanced` 将计算结果存入影子缓冲区。
6.  **SRAM累加 (SRAM Accumulation)**: `sa_enhanced` 将影子缓冲区的结果与C-SRAM中的值累加。

下面我们将根据日志，详细分析每个阶段的耗时和具体工作。时钟周期为 **10ns**。

### 各阶段详细时序分析 (完整流程)

#### 阶段一: 数据加载 (Data Loading)

*   **模块**: `loader.v`, `sram_banked.v`
*   **触发**: 外部控制器在 `55,000 ps` 后发出 `load_req` (日志中未直接显示，但可推断)。
*   **过程**:
    1.  `loader` 模块收到请求，进入 `S_LOADING` 状态。
    2.  它需要为A和B两个16x16的SINT8 tile加载数据。每个tile为 `16*16 = 256` 字节。
    3.  主存接口位宽为64位（8字节），因此每个tile需要 `256 / 8 = 32` 次内存读取。
    4.  总共需要加载 `32 (A) + 32 (B) = 64` 个64位字。
    5.  `loader` 采用流水线方式发出64个读请求，并接收64个读响应。每收到一个响应，就将其写入对应的 `sram_banked`。
*   **起止时间与耗时**:
    *   **开始时间**: 我们可以从 `loader` 完成的时间点反推。
    *   **结束时间**: 日志明确指出 `[745000] [LOADER] INFO: Load request completed.`。这表示在 **745,000 ps**，第64个数据字已经成功写入SRAM。
    *   **总耗时**: 从日志来看，系统在 `55,000 ps` 启动。如果假设控制器在 `65,000 ps` (1个周期后) 启动加载，那么加载过程耗时 `745,000 - 65,000 = 680,000 ps`，即 **68个周期**。
        *   *分析*: 这68个周期很可能包括：发出最后一个（第64个）请求需要64个周期，加上主存的固定读延迟（request-to-response latency）。`68 - 64 = 4`，这表明你的模拟环境中主存有 **4个周期** 的读延迟。

#### 阶段二: 流水线同步 (Pipeline Synchronization)

*   **过程**: 在`loader`完成工作后，顶层控制器并不会立即启动计算。它需要进行状态同步，并以正确的时序启动下游模块。
*   **起止时间与耗时**:
    *   **开始时间**: **745,000 ps** (`loader` 完成)。
    *   **结束时间**: **785,000 ps** (下一个阶段开始)。
    *   **总耗时**: `(785,000 - 745,000) ps / 10,000 ps/cycle = **4个周期**`。
    *   **内容**: 这4个周期是控制器逻辑的内部延迟。控制器在755k ps检测到`load_done`，然后等待3个周期，在785k ps发出第一个启动信号。

#### 阶段三: 数据格式化与馈送 (Data Formatting & Feeding)

*   **模块**: `data_formatter.v`
*   **核心对齐逻辑 (DF与SA)**: 这是理解整个流水线启动的关键。
    *   `data_formatter` 内部有一个 **2个周期** 的数据通路延迟（从发出SRAM地址到数据在最终输出级可用）。代码中的 `PIPELINE_COMPENSATION = 2` 体现了这一点。
    *   为了让脉动阵列（SA）在第0个计算时刻（`t_feed=0`）能接收到第一批有效数据，`data_formatter` 必须 **提前2个周期** 开始工作以“预热”其内部流水线。
    *   控制器通过 **错开** `start_pass` (给DF) 和 `start_new_k_iteration` (给SA) 的断言时间来实现这种对齐。

*   **时序分解**:
    *   **785,000 ps**: 控制器断言 `start_pass` 给 `data_formatter`。DF进入 `S_STREAMING` 状态，其内部 `time_cnt_q` 复位为0。它发出SRAM读地址，用于准备 `t_feed=0` 的数据。
    *   **795,000 ps**: 控制器断言 `start_new_k_iteration` 给 `sa_enhanced`。
        *   同时，DF的 `time_cnt_q` 变为1。它发出SRAM读地址，用于准备 `t_feed=1` 的数据。
        *   SA收到复位信号，其FSM从 `IDLE` 切换到 `CALCULATING_PK`，PE内部状态复位。
    *   **805,000 ps**:
        *   DF的 `time_cnt_q` 变为2。此时，为 `t_feed=0` 读取的数据已经通过了2级流水线，**DF开始向SA输出第一批有效数据**。
        *   SA的 `activate_pe_computation` 信号变为高电平，PE阵列被使能。
        *   **完美对齐**: SA在被使能的第一个周期，就收到了来自DF的第一批有效数据。日志 `[805000] [PE_RECV(0,0)] Valid inputs received` 证实了这一点。
*   **总耗时**: 数据馈送过程与PE计算过程完全重叠。整个馈送过程（从`t_feed=0`到`t_feed=46`）持续 `47` 个周期，从 `805,000 ps` 到 `805,000 + 46*10,000 = 1,265,000 ps`。
